## Question

Formalize the parsing rules currently shown only by example: "last token owns following indented lines"; when parens are required vs optional (`a (b c)` vs `a(b c)` vs `a b c`); comma-tuple vs space-separated arguments; operator precedence table for the infix set (`+ - * / // % > < >= <= != == & | ^ >> <<` and logical operators, which are currently missing from the doc); whether `if` gets its own arity rule; the exact meaning of multi-line lambda bodies. Deliverable: rules precise enough that two implementers parse the same program identically; a prototype grammar draft may be wanted before locking.

**Resolution (closed 2025-09-01, auto-run):**
- **Indentation ownership (the doc's rule, formalized):** the LAST token of a line owns the following deeper-indented lines; sibling lines at the same depth are sibling arguments of that owner. So `a b\n  c` is `a(b(c))` (c belongs to b) while `a\n  b\n  c` is `a(b, c)` — the doc's quirk is normative.
- **Same-line calls:** space-separated tokens after a head are sibling arguments (`a b c` = `a(b, c)`).
- **Parens:** `f (…)` ≡ `f(…)` — the paren is f's arglist. Inside an arglist, top-level `,` separates arguments and spaces chain nested calls: `f (a b, c d)` = `f(a(b), c(d))`. Bare `(x)` groups; `()` is a zero-arg call; `,` builds tuples (`3,4`).
- **Postfix:** `.` attribute and `a[i]` subscript bind tightest; `a.b c` = method call `a.b(c)`. Basic slices `a[i:j]` included.
- **Operators (owner correction, 2025-09-01):** infix operators are always **symbols glued to their LHS** — `a& b`, `a+ b`, `x== y` are valid; a space before the operator (`a & b`) and word-infix (`a and b`) do not exist. `not` is a regular prefix function; `and`/`or` are prefix functions (`and a b`, `or a b`), evaluated eagerly — the short-circuit idiom is an explicit thunk: `and a (: b)`. Symbol precedence follows Python's table (`&` above `|`, comparisons below arithmetic); comparisons chain Python-style.
- **Lambda `:`** binds loosest — the body extends to end of line or owned block; params before `:`, bare `:` = zero-param.
- **Misc:** `;` separates expressions on one line; `#` comments; string/number literals adopt Python syntax verbatim (incl. f-strings); truthity = Python truthiness; `import name` is special syntax binding the module object (mechanism: ticket 014).

**Amendment (owner review, 2025-09-01):** `,` and `;` are **removed from the language** — one expression per line, indentation for blocks, parens for grouping/arglists. The infix glue rule tightens: **every infix operator must be glued to its left operand** — `a& b| c` ✓, `a& b | c` ✗ (an operator with nothing glued before it is a syntax error); override precedence with parens: `(a& b)| c` or `a& (b| c)`. `[ ]` is **subscript**, not a list literal, with the same grammar inside: `xs[slice 1 3]` = `xs[slice(1, 3)]` (slices via the `slice` constructor — no slice syntax); list literals are calls (`list 1 2 3`); destructuring is `(a b)= list 3 4`. Paren-arglists attach to the nearest head: `f (a) (b)` = `f(a, b)`; call a returned function via grouping: `(make_adder 3) 5`.

**Amendment 2 (owner review):** **bracket duality**: glued `a[i]` = subscript; space-separated/standalone `[a b]` = list literal (elements space-separated, same inner grammar — `[a b]` is a list, `a [b]` passes the list [b] to a). **Comma returns as the tuple builder**, lowest precedence: heterogeneous values in tuples, homogeneous in lists (`(a b)= 3, 4`; `f (a, b)` passes one tuple). **Parameter annotations** (param lists are name-list context, so `:`/`=` take param meanings): `name(:type)?(=default)?`, vararg `..(:type)?`, kwarg `...(:type)?`, and a trailing nameless `:type` = return type: `add= (a:int b:int :int): a+ b`. `..`/`...` are ordinary special variable names in the body. **Call-site kwargs** use `name:=value` — a fresh operator, deliberately distinct from `=` (assignment expression), `==` (bool argument), and `:` (lambda argument); kwargs come after positionals (Python order). `:=` has very high precedence — higher than adjacency-call — so no parens are needed: `connect "example.com" port:= 8080`. **Infix binds tighter than the argument boundary:** an adjacency argument is a maximal infix expression, so `int a/b` = `int(a/b)` and `f x+ y` = `f(x+ y)` — separate args need `f x y` or parens. Annotations are documentation-only in v1 (no runtime enforcement); no generics for now. **`:` body parsing:** a same-line body is ONE expression — `: a b c` = `lambda: a(b, c)`, not a sequence; multi-statement bodies must be indented blocks. Parsing needs no special-case logic: a Pratt/recursive-descent parser with the symbol precedence table, the glue/no-glue lexical distinction, and param-list mode (a paren group followed by `:`) covers everything.

**Arity note (owner clarification):** the compiler knows every infix operator and its fixed arity (one LHS, one RHS for most) — an infix never acts as a variadic head, so `a= x+ f 3` is never `+(x, f, 3)`: it parses as `x+ (f 3)`, because adjacency-call arguments attach only to heads (atoms/postfix chains like `f`, `q.r`, `xs[i]`), never to infix results; to call a sum, group it: `(x+ f) 3`. **Subscript arity:** getitem takes exactly one index expression — `a[b c]` is `a[b(c)]`; multiple indices need an explicit tuple: `a[b, c]`. **Unary:** the lexer folds `-<digits>` into a negative literal token; expression negation is `0- x` or library `neg` — a detached `-` is never an operator.
