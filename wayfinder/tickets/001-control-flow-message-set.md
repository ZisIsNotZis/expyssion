## Question

Under S1⁺ (ADR 0001), should `return/break/continue` and `raise` ride the Result channel as message kinds (fully uniform: every frame-crossing is a handled effect, everything shadowable), or stay native Python exceptions crossing greenlet boundaries (cheaper, simpler interop with real Python code, one non-uniformity in the protocol)? Decide the exact message vocabulary of the Result channel, what each kind means for handler resolution, and what happens when a message reaches the main greenlet unhandled.

**Resolution (closed 2025-09-01):** Minimal two-tube vocabulary. **Upward (effect requests, child → parent):** `Yield(v)` and `Done(r)` only. **Downward (answers, parent → child):** `Start(args)` on first switch, `Resume(v)` as the reply to a suspended effect — Resume is not a channel message but the value passed by the handler's switch, i.e. the return value of `_yield(v)`. `return/break/continue` compile to internal `BaseException` subclasses with **no depth parameter and no crossing counts**; user `try` catches `Exception` only, so control-flow exits are un-interceptable and `KeyboardInterrupt` passes through (cancellation is ticket 011's). `raise` is a native Python exception; `try` catches native exceptions at its sync point, so Python-origin errors are catchable uniformly. Unhandled `Yield` reaching the main greenlet is a loud runtime error ("unhandled yield outside generator context"); unhandled native exceptions propagate to Python.

**Amendment (same-day review, second revision; supersedes the crossing-count and blanket-shadowability clauses of the first draft and the birth-body phrasing of the first amendment):** `return v` raises an internal ReturnException that bubbles the **dynamic stack**. Every lambda invocation frame carries a compile-time flag from its construction position: **assigned** (born as an `=`-RHS) or **consumed** (born as any function call's argument). Assigned frames catch ReturnException and convert it to a normal return of that lambda invocation; consumed frames and runtime-function frames (if/for/try implementations) pass it through. So `f= : a ; return b ; c` makes f return b; `f= : if c1 : if c2 : if c3 : return v` jumps through all three ifs and makes f return v; and `ret= : return v` invoked deep inside other structures breaks nothing — ret catches its own return (in a trivial body it is equivalent to `ret= v`). A return reaching the main greenlet with no assigned frame above it is a loud error ("return outside function"). Sharp edge: `f= : h (: return 3)` — the callback's return returns **from h** at the invocation point (h's remaining body skipped, f continues), because h is the nearest assigned frame. Implementation note: one flag and one wrapper per lambda — no tags, no counters. Rejected alternative ("a stored lambda's return aborts its storing frame") as incoherent: every lambda is born from `=` or an argument, so that rule regresses — `f= : a ; return b` would abort f's definer. `break`/`continue` are dynamic: only loop implementations catch them, all other code ignores them, no active loop → loud error; `continue` needs no resumable machinery (the raising body invocation is abandoned either way). Shadowing: `return/raise/try/break/continue` remain shadowable; **`=` and `:` are hard-wired syntax** (magical LHS and parsing) and cannot be shadowed; other infix operators are technically shadowable (allowed, documented as unusual). Return compilation is purely positional — the compiler needs no binding resolution for it; binding resolution remains an obligation only for sync-point elision (ticket 013). Rejected: Err-on-channel (duplicates native exception catching at every `try`, pays N×2 switch bubbling, seam must convert back anyway); all-messages-on-channel (user handlers could intercept control flow unless private kinds reintroduce non-uniformity). Note for ticket 002: the yield *receiver* question (who handles `Yield` — collector handlers like `list/dict/set` vs lexical marking vs explicit `generator` wrapper) is 002's decision; this ticket only fixed that the channel carries the request and the handler answers via Resume.
